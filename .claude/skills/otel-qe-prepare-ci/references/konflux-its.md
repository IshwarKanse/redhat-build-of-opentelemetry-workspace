# Konflux integration tests (new ART group)

How to check the results of the scenarios is in `otel-art-reference` ([RELEASE.md](../../otel-art-reference/RELEASE.md#check-integration-test-results)). The pipelines are described in the README of `konflux/integration-tests` in `distributed-tracing-qe`. The sections below cover what the person who maintains the scenarios needs.

The pipelines have no per-release parameters: their first task, `resolve-release`, reads the release from the FBC under test and from the `rhosdt-<art version>` branches at run time. Only the scenarios name the release, and only the latest release is supported and tested, so a new ART group replaces the scenarios of the previous release.

### New ART group (every major or minor version, a new `rhosdt-*` branch, for example `0.159`)

1. **Check the conventions** that `resolve-release` relies on: the Konflux application `fbc-rhosdt-<major>-<minor>` exists in `art-rhosdt-tenant` (ART creates it with the new group; a scenario for an application that does not exist never runs, so open the merge request after ART has onboarded the group), the branch `rhosdt-<art version>` exists in `openshift/open-telemetry-opentelemetry-operator` and in `openshift/redhat-opentelemetry-collector`, `versions.txt` has the keys `operator`, `opentelemetry-collector` and `targetallocator`, and `manifest.yaml` of the collector has `dist.version`.
2. **Replace the scenarios** in `konflux-release-data`, in `tenants-config/cluster/kflux-ocp-p01/tenants/art-rhosdt-tenant/otel-integration-tests.yaml`: set the application (`fbc-rhosdt-<art version with dashes>`) and the names of the scenarios (`otel-e2e-tests-4-14-<art version with dashes>`, `otel-e2e-tests-4-22-<art version with dashes>`, `otel-upgrade-tests-4-22-<art version with dashes>`), and remove the scenarios of the previous group. Check the OCP versions too: the e2e scenarios run on the minimum and the maximum supported OCP version, and only the one with `run_dast` runs the DAST scan. The DAST results folder and the `rhosdt_version` parameter: "Operating the scenarios" below. The scenarios are optional, use the context `push`, and run the pipelines of `distributed-tracing-qe` from `main`.
3. **Regenerate the manifests** from `tenants-config`: `./get-kustomize.sh <dir>` downloads kustomize, and `./build-single.sh art-rhosdt-tenant <dir>/kustomize` rewrites the files under `tenants-config/auto-generated/`. The YAML file must start with `---`, or the yamllint check of the merge request fails.
4. **Open the merge request** to `releng/konflux-release-data` with one commit, rebased on `main` so that it can be fast-forwarded, and wait for the checks. Run `tox -e tenants-config-test` first if you can; it is the check of the repository.
5. **Check the first runs** after the merge: the scenarios start with the next FBC build of the new group. See `otel-qe-release-testing` for how they are checked, and `otel-art-reference` for how to check and re-run them.

### When to change the pipelines

Only to change the tests themselves: the `skip_tests` list, the supported OCP versions (`ocp_version` of the scenarios in `konflux-release-data`) or the logic of a task. The ITS run the pipelines from `main` of `distributed-tracing-qe`, so a merge changes every following run. Test a change first with a temporary scenario (context `disabled`, `revision` of the resolver set to your branch) that you start by labelling a Snapshot, and remove it afterwards.

### Operating the scenarios

- **Which run is which:** every build round of ART makes one Snapshot per supported OCP version. Each scenario starts on every Snapshot, and a run for another OCP version than its own ends in about 30 seconds with success. Only the Snapshot of the scenario's OCP version gets a real run. The OCP version of a Snapshot is the suffix of its `test.appstudio.openshift.io/result-image-url` annotation (`...ocp4.22`).
- **Results:** only the last 3 PipelineRuns are kept. The result of each scenario stays on the Snapshot, in the annotation `test.appstudio.openshift.io/status` (`TestPassed`, `TestFail`, `InProgress`).
- **Re-run:** the label is removed when the run starts. Konflux does not start a second run of the same scenario on a Snapshot while one is in progress, and a running run can only be cancelled by an admin of the tenant.
- **Access:** a maintainer can read PipelineRuns, TaskRuns, pods and logs, and can manage scenarios and patch Snapshots, but cannot read events or Secrets, or cancel or delete a PipelineRun. For those, ask ART (`#wg-art-lp-onboarding`). If other sessions share the kubeconfig, pass `--context` (or use a separate `KUBECONFIG`) because a login to another cluster replaces the default context.
- **Failed run:** look at the task that failed. `resolve-release` fails for one of two reasons. Either a naming convention does not hold (the message names the source), or the FBC is older than the branch ("the FBC installs the operator X, but versions.txt on the branch says Y"): that is normal right after the version of the branch was bumped and before the first FBC build of that version, and the next build is tested, so there is nothing to do. `provision-cluster` means OpenShift CI did not give a cluster in time (20 to 55 minutes is normal, the wait is 75 minutes), so run it again. `add-stage-credentials` means the Secret `stage-registry-creds` (key `.dockerconfigjson`) is missing in the tenant. The later tasks are failures of the product or of the tests.
- **DAST results:** the RapiDAST scan of the e2e scenario with `run_dast` uploads its results to the GCS folder `rhosdt/<art version>/otel` (for example `rhosdt/0.158/otel`). To use the product version as the folder name (for example `rhosdt/3.12/otel`), set the optional parameter `rhosdt_version` of that scenario in `konflux-release-data`; leave it unset to use the ART version. Other optional parameters of the e2e pipeline are `otel_tests_branch` (the tests branch, default the `rhosdt-<art version>` branch) and `skip_tests`.
- **Secrets in the tenant:** `stage-registry-creds` (pulls the ART images from `registry.stage.redhat.io`) and `rapidast-sa-rhosdt-key` (key `sa-key`, uploads the RapiDAST results to GCS). Only an admin of the tenant can create them.
- **Clusters:** the pipelines get OpenShift CI clusters from the cluster profile `aws-konflux-prod`, which is set in the `provision-cluster` task of the pipelines, not in the scenarios.
