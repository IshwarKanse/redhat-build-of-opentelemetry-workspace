# OBI RHOSDT 3.12 Improvements — Design

## Context

The OBI (OpenTelemetry eBPF Instrumentation) Receiver was introduced in RHOSDT 3.11 as a Technology Preview collector receiver. The 3.11 release supports HTTP traces and RED metrics with basic workload selection (`k8s_namespace` + `k8s_pod_labels`) and Kubernetes attribute enrichment.

The upstream OBI project (v0.x, `development` stability) has a much broader feature set. This design defines which upstream capabilities to bring into RHOSDT 3.12, plus operator improvements for deployment at scale.

## Scope

All features remain **TP (Technology Preview)** — upstream OBI is v0.x with no per-feature stability tiers.

### In scope

1. **Context propagation** — enable distributed tracing across OBI-instrumented services
2. **Metrics features** — span metrics, service graph, network flow, TCP stats
3. **Extended service discovery** — additional workload selectors and exclusion rules
4. **Log-trace correlation** — inject trace/span IDs into application logs (pending receiver-mode verification)
5. **k8s-cache** — new Red Hat-built container image + operator-managed deployment for large clusters
6. **APM dashboard compatibility** — verify OBI span metrics work with the OpenShift APM dashboard

### Out of scope

- Runtime metrics (JVM heap/GC, Node.js event loop) — deferred
- Operator auto-RBAC/SCC/volumes — deferred, more complex than initially assessed
- Dedicated OBI CRD — upstream consensus is OBI stays as a collector receiver
- OBI config v2 — upstream draft, not implemented
- GenAI instrumentation, GPU/CUDA, payload extraction, routes decorator — not prioritized for 3.12

## Approach

Single approach selected: extend the existing collector receiver integration, no new CRDs. All OBI config is under `spec.config.receivers.obi` in the `OpenTelemetryCollector` CR. The k8s-cache follows the Target Allocator pattern for operator-managed auxiliary deployments.

### Why this approach

- Aligns with upstream operator direction (issue #4571 discussion) — OBI deployed via collector CRD
- Minimizes operator API surface changes — only one new CRD field (`obiMetadataCache`)
- All new receiver features are pure config additions, no operator code needed
- The Target Allocator pattern is proven and well-tested for managing auxiliary deployments

## Design

### 1. Context Propagation

Adds `ebpf.context_propagation` to the OBI receiver config with four modes:

- `headers` — W3C `traceparent` in HTTP headers (most common)
- `tcp` — TCP options for non-HTTP protocols
- `all` — both mechanisms
- `disabled` — default, isolated per-service spans

The deprecated upstream `ip` mode is not documented or supported.

**Impact:** Receiver config only. No operator changes. No new RBAC.

### 2. Metrics Features

Four new feature groups enabled via `meter_provider.features`:

| Group | What it adds |
|---|---|
| Span metrics (`application_span_otel`) | `traces_span_metrics_calls_total`, `traces_span_metrics_duration` — matches `spanmetricsconnector` output |
| Service graph (`application_service_graph`) | 4 metrics matching `servicegraphconnector` output |
| Network flow (`network`, `network_flow_packets`, `network_inter_zone`) | 3 metrics for bytes, packets, inter-zone traffic |
| TCP stats (`stats`, `stats_tcp_rtt`, `stats_tcp_retransmits`, `stats_tcp_io`, `stats_tcp_failed_connections`) | 4 metrics for TCP connection observability |

Each group is independently togglable. No additional eBPF capabilities required beyond what the base receiver needs.

**APM Dashboard Compatibility:** The OpenShift APM dashboard expects `spanmetricsconnector` output format. OBI's span metrics are close but there is a known discrepancy: OBI emits `traces_span_metrics_calls_total` while the dashboard expects `traces_span_metrics_calls` (without `_total` suffix). This must be verified — Prometheus may normalize the suffix depending on exposition format, or a relabel workaround may be needed.

**Impact:** Receiver config only. No operator changes.

### 3. Extended Service Discovery

The 3.11 docs cover only `k8s_namespace` + `k8s_pod_labels`. Upstream supports:

- Kubernetes selectors: `k8s_deployment_name`, `k8s_statefulset_name`, `k8s_daemonset_name`, `k8s_pod_name`, `k8s_pod_annotations` (all glob-capable)
- Process selectors: `open_ports`, `exe_path`, `languages`
- Exclusion: `exclude_instrument` (same format as inclusion, takes precedence), `exclude_otel_instrumented_services` (default: true, prevents double-instrumentation)

Selection logic: within an `instrument` entry selectors are AND-ed; multiple entries are OR-ed.

**Impact:** Receiver config and docs only. No operator changes.

### 4. Log-Trace Correlation

The `ebpf.log_enricher` feature injects trace/span IDs into application log files on the host filesystem. Works with JSON and plain-text log formats. No additional eBPF capabilities needed.

**Risk:** The upstream v2 design (not yet implemented) explicitly flags log enrichment as standalone-only due to the write side-effect (modifying files on disk). In the current v1 code, the config is passed through to the receiver, but whether it actually works correctly in receiver mode must be verified. If verification fails, this feature is removed from 3.12 scope.

**Impact:** Receiver config only if it works. Verification task is a prerequisite.

### 5. k8s-cache — Operator-Managed Metadata Cache

#### Problem

On large clusters, each OBI DaemonSet pod runs its own Kubernetes informer (watching pods, services, nodes). This creates O(N) watch streams against the API server, where N is the number of nodes.

#### Solution

The k8s-cache is a standalone gRPC service that centralizes informer watches. All OBI pods connect to one cache instance instead of running local informers.

#### Architecture

- **Binary:** `cmd/k8s-cache/main.go` — standalone Go binary
- **Protocol:** gRPC on port 50055 (default), `informer.EventStreamService/Subscribe` RPC
- **Behavior:** Runs informers, replays full snapshot on subscription, streams add/update/delete events
- **RBAC:** `list`+`watch` on pods, services, nodes (core API) and replicasets (apps API)
- **Security:** Insecure gRPC (no TLS) — both components run within the same cluster

#### Operator integration

Follows the Target Allocator pattern — an embedded struct in the `OpenTelemetryCollector` CRD:

```yaml
spec:
  obiMetadataCache:
    enabled: true
    image: <auto-populated>
    replicas: 1
    resources: ...
```

When enabled, the operator:
1. Creates Deployment, Service, ServiceAccount, ClusterRole/ClusterRoleBinding
2. Auto-sets `attributes.kubernetes.meta_cache_address` in the OBI receiver config
3. Manages full lifecycle alongside the collector CR
4. Validates: only allowed in `daemonset` mode with an `obi` receiver

The CRD field name needs upstream alignment before implementation.

#### Productization

- New Dockerfile in `konflux-opentelemetry` (UBI9 base)
- New Konflux Application/Component definition
- Add to FBC catalogs
- Multi-arch: amd64 and arm64 only

#### Research prerequisite

Before implementing, profile API server load on representative OCP cluster sizes (10/50/200 nodes) to:
- Quantify resource savings from the cache
- Determine the cluster size threshold where the cache is worthwhile
- Set default resource requests/limits
- Write sizing guidance for docs

### 6. APM Dashboard Compatibility

A verification task to ensure OBI's `application_span_otel` metrics produce the same dashboard experience as the `spanmetricsconnector`. The APM dashboard is external to this workspace (likely in COO). The verification must cover metric names, attribute names, and Prometheus exposition format.

## Verification Tasks

| Task | Prerequisite for |
|---|---|
| Verify OBI span metrics compatibility with APM dashboard | Metrics features documentation |
| Verify `_total` suffix handling (Prometheus normalization) | Metrics features documentation |

| Profile API server load with/without k8s-cache on OCP clusters | k8s-cache implementation |
